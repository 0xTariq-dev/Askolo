### 2. Update Project Memory: Step-by-Step Operational Workflows

#### Standard Feature Deployment Workflow
When pushing updates through the pipeline under normal conditions, execute these steps in order:
1. Break features down into small, structural **Micro-PRs**. Merge these micro-PRs sequentially into `main`.
2. Ensure incomplete backend features or endpoints are hidden via unexposed routing endpoints (Dark Launching) to maintain system stability.
3. When ready to promote to staging, generate an immutable Git tag from the tip of `main`:
   ```bash
   git tag -a v1.0.0-rc1 -m "Release Candidate 1 for Version 1.0.0"
   git push origin v1.0.0-rc1
   ```
4. Access the **Staging Repl (Repl #2)**, fetch and checkout the tag `v1.0.0-rc1`, and run validation checks.
5. Once staging passes, cut the official production stable tag from that same verified commit:
   ```bash
   git tag -a v1.0.0 -m "Production Release Version 1.0.0"
   git push origin v1.0.0
   ```
6. Access the **Production Repl (Repl #3)**, pull the unique `v1.0.0` tag, and trigger a workspace redeployment.

#### Emergency Hotfix Workflow (Production-Baseline Isolation)
If a critical production bug occurs while the `main` trunk contains unfinished or half-baked micro-PR features, **never cut a production patch from the tip of main.** Follow this exact isolation recovery path:
1. **Isolate the Baseline:** From your local workspace or Dev Repl, check out the exact Git tag currently running in production into a new short-lived hotfix branch:
   ```bash
   git checkout tags/v1.0.0 -b hotfix/v1.0.1
   ```
2. **Apply Patch:** Write, debug, and complete the hotfix logic strictly within this temporary `hotfix/v1.0.1` branch.
3. **Verify via Staging:** Pull the `hotfix/v1.0.1` branch into the **Staging Repl (Repl #2)** to verify the patch functions correctly within an isolated environment.
4. **Tag the Isolated Patch:** Create a unique immutable production tag directly from this temporary branch:
   ```bash
   git tag -a v1.0.1-hotfix -m "Isolated production hotfix patch for bug"
   git push origin v1.0.1-hotfix
   ```
5. **Deploy to Production:** Open the **Production Repl (Repl #3)**, fetch and check out the tag `v1.0.1-hotfix`, and restart the workspace to go live.
6. **Reconcile the Trunk (Prevent Regression):** Return to the main branch, cherry-pick the specific hotfix commit, push to the remote repository, and permanently delete the local hotfix branch:
   ```bash
   git checkout main
   git cherry-pick <hotfix-commit-hash>
   git push origin main
   git branch -D hotfix/v1.0.1
   ```

### 3. Core Guardrails and Constraints for Agent Execution
Ensure the following absolute enforcement rules are integrated into project guidelines:
- **Zero Permanent Branching:** No persistent `development`, `staging`, or `production` branches are allowed. `main` is the only source-of-truth branch.
- **Temporary Lifecycles:** Hotfix branches are throwaway structures. They must be destroyed immediately after a successful cherry-pick reconciliation.
- **Backward Compatibility:** All database changes must utilize expand-and-contract scripts (e.g., adding columns without deleting legacy fields in the same step) to prevent cross-project database state corruption during independent tag deployments.
